# Grill-Me：需求追问澄清

> **原则：先问清楚再动手，宁可多问 3 分钟，不要返工 3 小时。**

## 项目流程接入

本技能是 [assemble-platform-workflow](../assemble-platform-workflow/SKILL.md) 的 Phase 0 执行者。需求共识确认后，把「影响范围」交给主流程做技能路由：跨 `apps/services/packages` 两层以上加载 [senior-fullstack-engineer](../senior-fullstack-engineer/SKILL.md)，涉及 Babylon/glTF/GLB/Web3D 加载 [senior-web3d-engineer](../senior-web3d-engineer/SKILL.md)，两类同时命中则共同加载。过程中的纠正与知识缺口交给 [self-improving-agent](../self-improving-agent/SKILL.md) 记录。

---

## 什么时候触发

收到以下任意信号时，**先不要开始写代码**，先加载本 skill 进行追问：
- 用户说"帮我做/加一个/改一下/优化一下"某功能
- 进入 Phase 0（需求澄清与版本规划）
- 需求描述不够具体（只有目标没有边界）
- 涉及跨层改动（前后端都动、契约要改、数据模型要变）

---

## 追问框架（GRILL 五问法）

按顺序抛给用户提供答案，用户已经给够信息的自答跳过：

### 1. Goal（目标）
> 这件事最终要达成什么结果？用一句话描述成功状态。

- 用户视角：做完之后谁用起来，感觉到什么不同？
- 系统视角：哪个模块/接口/页面发生变化？

**判断**：能写出一句"当用户 X 时，系统会 Y，产生 Z 结果"吗？不能 → 继续追问。

### 2. Range（边界）
> 做什么、**不做什么**？

明确列出：
- ✅ 本次要做的：（3-5 条）
- ❌ 明确不做的：（至少 1 条，防止范围蔓延）

**铁律**：用户没提的功能一律砍掉或先问，不准自作主张加。

### 3. Inputs & Constraints（输入与约束）
- 输入从哪来？（用户填 / API 传 / 数据库查 / LLM 生成）
- 有没有外部依赖？（LLM / DB / 第三方 API / 文件 I/O）
- 性能要求？（响应时间、并发量）
- 兼容性？（浏览器、Python 版本、现有接口契约）
- 有没有硬约束？（如"不能改数据库 schema""必须走现有的审批流"）

### 4. Logic（核心逻辑）
> 数据/状态怎么流转？

- 状态机：有哪些状态？怎么切换？
- 决策规则：什么条件走哪条分支？
- 降级策略：外部依赖挂了怎么办？
- 幂等性：重复请求会怎样？

**输出**：用伪代码或流程图描述核心路径。

### 5. Legacy（验收标准 + 兼容性）
> 怎么算做完了？旧东西会不会坏？

**验收标准**（必须可验证）：
- [ ] 条件 A → 结果 B（可观察的现象）
- [ ] 边界条件 C → 结果 D

**回归检查**：
- 哪些现有功能可能受影响？
- API 契约要不要改？（改了要同步 docs/api-contract.md）
- 数据模型要不要变？（变了要写 migration）

## 追问节奏

1. **第一轮**：抛出 GRILL 五问，给用户填空
2. **第二轮**：根据用户回答，补充遗漏（用户答了 Goal 但没说边界 → 追问 Range）
3. **第三轮**（可选）：用户有分歧/模糊 → 给出 2-3 个方案让用户选
4. **收敛**：把所有确认点整理成一段「需求共识」发回给用户，让用户确认"对的，就按这个来"

> ⚠️ 用户说了"对"之后才能进入 Phase 1 分支开发。

---

## 输出格式

追问完成后，输出一段标准化的需求共识，格式如下：

```
## 需求共识

**目标**：[一句话]
**范围**：
- ✅ 做：[列表]
- ❌ 不做：[列表]
**输入**：[来源]
**约束**：[技术/性能/兼容性约束]
**核心逻辑**：[一句话或伪代码]
**验收标准**：
- [ ] [可验证的条件]
**影响范围**：[后端/前端/契约/DB]
```

## 示例对话

**用户**："帮我在审批页加个搜索"

**Grill-Me**：
> 收到，先确认几个点再动手：
>
> 1. **目标**：在 /approvals 页面上方加搜索框？搜索内容是审批 ID 还是任务 brief？
> 2. **边界**：只搜已审批的还是包含历史审批？分页要不要一起改？
> 3. **约束**：后端加搜索参数 / 前端只做展示？现有分页接口要不要兼容？
> 4. **验收**：搜索"关键词"后只返回包含该词的审批卡片？空搜索显示全部？
>
> 请确认以上，我再进入开发。

**用户**："搜 brief，只搜待审批的，后端加参数，分页兼容"

**Grill-Me 收敛**：
```
## 需求共识
**目标**：/approvals 页面加搜索框，按任务 brief 模糊过滤待审批项
**范围**：
- ✅ 做：搜索框 UI + 后端 search 参数 + 模糊匹配 brief
- ❌ 不做：不搜历史已审批、不改分页接口、不搜 approval_id
**输入**：前端 input 实时防抖搜索
**约束**：后端已有分页接口，search 作为可选参数，空搜索等价于无过滤
**核心逻辑**：GET /api/v1/approvals?search=xxx，后端按 brief 模糊过滤后分页返回
**验收标准**：
- [ ] 搜索"苹果"返回 brief 含"苹果"的审批
- [ ] 空搜索返回全部
- [ ] 搜索不存在内容返回空列表
**影响范围**：后端 approvals.py + 前端 page.tsx
```
> 请确认，确认后进 Phase 1。
